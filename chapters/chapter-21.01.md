# Глава 21.1. HtmlCanvasElement: размеры и HiDPI

## 21.1.1. О чём эта подглава

Первое, что нужно понять про `<canvas>`, — что это **два разных размера**. Один — размер буфера рисования, тот самый массив пикселей, в который мы пишем. Второй — размер элемента на странице, тот прямоугольник, который видит пользователь. Обычно они совпадают. На Retina-экранах — не должны.

Эта подглава — про то, почему так, и как с этим работать. Тема кажется мелкой, но это ловушка №1 для всех, кто впервые ставит `<canvas>`. Код работает, картинка рисуется, всё выглядит нормально на ноутбуке разработчика, а на Retina-мониторе или при зуме страницы получается мутное пятно. Разница между «работает» и «работает правильно» здесь в трёх строках кода.

## 21.1.2. Что вообще такое `<canvas>`

`<canvas>` — это HTML-элемент, который представляет собой **растровое полотно**. Внутри него нет DOM-узлов, нет детей, нет CSS-стилей для содержимого. Есть только пиксели. Можно нарисовать точку, линию, прямоугольник, изображение — и всё это окажется в буфере элемента, а браузер покажет буфер как картинку.

Два способа создать `<canvas>`:

**Первый — в разметке.** `<canvas id="my-canvas"></canvas>` — обычный тег, к которому потом обращаются через `getElementById`.

**Второй — программно.** `document.createElement("canvas")` — так делают для OffscreenCanvas-подобных вещей, для временных холстов, для скрытых буферов. Так же проще, когда всё демо строится из Rust — не нужно править `index.html` при каждой новой подглаве.

Разница между двумя способами только в способе получения элемента. Всё остальное — `getContext`, `width`, `height`, `style` — одинаково.

Третий вариант — `OffscreenCanvas` — вообще не элемент DOM. Это объект, который существует только в памяти. У него те же методы (`getContext("2d")`, `drawImage`, `getImageData`), но нет `.style`, нет `appendChild`, нет визуального представления. Используется, когда нужно обработать пиксели без отображения: например, нарисовать временное изображение и превратить его в PNG Blob. Это отдельная тема (см. 21.5 и 21.7), но упомянуть стоит: OffscreenCanvas — та же логика размеров, что у обычного, только без CSS-стиля.

## 21.1.3. Два размера, один элемент

Вот ключевой факт:

```html
<canvas id="c"></canvas>
```

```js
const c = document.getElementById("c");
c.width = 400;              // размер БУФЕРА, в пикселях
c.style.width = "400px";    // размер на ЭКРАНЕ, в CSS-пикселях
```

Это **две независимые величины**. `c.width` — сколько пикселей в буфере. `c.style.width` — сколько места элемент занимает на странице. Браузер берёт буфер и **растягивает** его до размера элемента. Если размеры совпадают — один к одному. Если нет — масштабирование, и оно видно.

Это как `<img>` с картинкой 100×100, растянутой через CSS на 400×400. Пиксели те же, но каждый отображается квадратом 4×4. Или как видео 720p, растянутое на 4K-телевизор — растёт не детализация, а размытость.

У `<canvas>` та же механика.

## 21.1.4. Откуда берётся `devicePixelRatio`

Проблема начинается с того, что **физические пиксели ≠ CSS-пиксели**.

CSS-пиксель — абстрактная единица, придуманная, чтобы верстка выглядела одинаково на разных экранах. Один CSS-пиксель — примерно одна сотая дюйма на типичном мониторе. Но у Retina-дисплеев Apple физических пикселей на дюйм в два раза больше. Чтобы надпись «16px» выглядела того же размера, что на обычном мониторе, браузер использует **два физических пикселя на один CSS-пиксель**.

Коэффициент называется `devicePixelRatio` (DPR):

```js
console.log(window.devicePixelRatio);  // 1 на обычном, 2 на Retina, 3 на некоторых Android
```

DPR зависит не только от железа. Он меняется, когда пользователь:

- зумит страницу (`Ctrl+=`) — DPR растёт пропорционально зуму;
- перетаскивает окно между мониторами с разной плотностью;
- включает режим повышенной контрастности или крупного текста в системе.

Значит, DPR — **не константа**. Его нужно читать в рантайме, а не запоминать один раз при старте.

## 21.1.5. Наивный подход и его цена

Самый распространённый код:

```js
canvas.width = 400;
canvas.height = 200;
canvas.style.width = "400px";
canvas.style.height = "200px";
```

На обычном экране (DPR = 1) это работает идеально. Один буферный пиксель = один физический = один CSS. Всё резко.

На Retina (DPR = 2) происходит следующее:

1. В буфере 400×200 пикселей.
2. Элемент занимает 400×200 CSS-пикселей.
3. Браузер знает, что 400 CSS-пикселей — это 800 физических.
4. Он растягивает 400-пиксельный буфер на 800 физических пикселей.
5. Каждый буферный пиксель превращается в квадрат 2×2 физических.
6. **Картинка размывается**.

Глаз видит мыло. Особенно заметно на:

- тонких линиях (1 CSS-пиксель превращается в размытую полосу шириной 2 физических);
- мелком тексте (буквы теряют форму);
- диагональных линиях (появляются зубцы или, наоборот, замыливание).

Это и есть классическая ошибка «мой canvas мыльный». Происходит не потому, что canvas плохой, а потому что мы проигнорировали DPR.

## 21.1.6. Формула HiDPI

Правильный код состоит из трёх строк:

```js
const dpr = window.devicePixelRatio;

// 1. Буфер — в DPR раз больше
canvas.width = cssWidth * dpr;
canvas.height = cssHeight * dpr;

// 2. Размер на экране — в CSS-пикселях
canvas.style.width = cssWidth + "px";
canvas.style.height = cssHeight + "px";

// 3. Контекст масштабируется
const ctx = canvas.getContext("2d");
ctx.scale(dpr, dpr);
```

**Первая строка** — увеличивает буфер. Теперь у нас 800×400 физических пикселей под ту же визуальную площадь.

**Вторая строка** — сохраняет CSS-размер. Элемент по-прежнему занимает 400×200 CSS-пикселей, никаких прыжков в вёрстке.

**Третья строка** — самая неочевидная. Без неё холст будет правильного размера, но всё нарисованное окажется в левом верхнем углу: canvas.width = 800 означает, что по умолчанию система координат идёт от 0 до 800. `ctx.scale(dpr, dpr)` растягивает систему координат обратно до 0..400. После этого `ctx.fillRect(0, 0, 100, 100)` займёт 100 CSS-пикселей, но физически будет 200 физических — резко, потому что буфер это позволяет.

Три строки — и результат выглядит так же чётко, как нативные приложения.

## 21.1.7. Границы разумного

DPR не бывает бесконечным. Практически:

- **Минимум 1** — стандартный экран.
- **Максимум 4** — «3x Retina» на дорогих телефонах плюс запас под высокий zoom.

Значения ниже 1 не встречаются, но защищаться стоит: некоторые тестовые окружения и расширения рапортуют произвольные числа. Значения выше 4 практически не встречаются, но если браузер вдруг отдаст 10 — умножать буфер в 10 раз глупо: 400×200 холст превратится в 4000×2000 = 32 МБ на буфер. Поэтому DPR климпится в диапазон `[1.0, 4.0]`.

Отдельный случай — `NaN` и `±∞`. `NaN` приходит, если что-то пошло не так в вычислениях выше по стеку, и безопасное значение для него — `1.0` (обычный экран). `+∞` — «очень большое число», естественный кламп — `4.0`. `-∞` и отрицательные — `1.0`.

Это ловушка: `f64::clamp` в Rust **не работает на `NaN`** — возвращает `NaN`, а не границу. Поэтому `NaN` нужно проверять отдельно:

```rust
fn clamp_dpr(dpr: f64) -> f64 {
    if dpr.is_nan() {
        return 1.0;
    }
    dpr.clamp(1.0, 4.0)
}
```

На `+∞` и `-∞` `clamp` работает корректно — первое прижимается к максимуму, второе к минимуму.

## 21.1.8. Как это выглядит в Rust

В Rust всё то же самое, только через web-sys. Два места требуют внимания.

**Первое — `style()`.** У `HtmlCanvasElement` нет метода `style()`. Он объявлен на `HtmlElement`, а web-sys не делает автоматического upcast'а между типами, даже если один наследует другой в DOM. Нужно явно:

```rust
let style = canvas.unchecked_ref::<HtmlElement>().style();
style.set_property("width", &format!("{css_w}px"))?;
```

`unchecked_ref` — безопасный upcast по цепочке наследования. Никакого рантайм-действия, просто смена типа ссылки.

**Второе — фича web-sys.** `style()` гейтится фичей `CssStyleDeclaration`. Без неё метода в API просто нет, и rustc говорит «no method named style» — не «нужна фича», а буквально «нет такого метода». Это правило web-sys: метод виден компилятору ровно тогда, когда включена его фича.

Альтернатива без фичи — `set_attribute("style", "width:400px;height:200px")`. Работает, но перезаписывает весь inline-стиль целиком. Для нашего случая безопасно, в общем случае — нет.

**Третье — контекст.** `getContext("2d")` возвращает `Object`, а не `CanvasRenderingContext2d`. Нужен downcast через `dyn_into`, который возвращает `Result<_, Object>`, а не `Result<_, JsValue>`. Это требует явного `.map_err`:

```rust
canvas
    .get_context("2d")?
    .ok_or_else(|| JsValue::from_str("no 2d context"))?
    .dyn_into::<CanvasRenderingContext2d>()
    .map_err(|_| JsValue::from_str("context is not CanvasRenderingContext2d"))
```

Всё это инкапсулируется в хелпер `get_2d_context` — вызывающий код просто пишет `let ctx = get_2d_context(&canvas)?;`.

## 21.1.9. Что показывает демо

Демо — два холста рядом, идентичный паттерн на обоих.

**Слева — «Naive»:** наивный подход. `canvas.width = 400`, `style.width = "400px"`. На обычном экране это выглядит так же, как HiDPI-вариант. На Retina — размыто.

**Справа — «HiDPI-correct»:** формула из трёх строк. На обычном экране неотличим от левого. На Retina — резкий.

Паттерн подобран так, чтобы разница была видна:

- **Сетка тонких линий** через каждые 20 CSS-пикселей — на наивном холсте превращается в серые полосы шириной 2 физических пикселя.
- **Диагональная синяя линия** шириной 1 CSS-пиксель — самый чувствительный элемент. На Retina без DPR она становится зазубренной или размытой.
- **Три окружности** с тонкой обводкой — контуры заметно теряют чёткость.
- **Мелкий текст 8px и 11px** — на наивном холсте буквы «плывут», на HiDPI остаются резкими.

Управление:

- **Слайдер CSS-ширины** (200..600 px) — меняет размер обоих холстов, позволяет увидеть, как меняется резкость при масштабировании. На наивном холсте чем больше CSS-размер, тем сильнее мыло.
- **Чекбокс «авто» + слайдер DPR override** — переключает между реальным DPR и принудительным. Позволяет **увидеть разницу на обычном экране**: поставьте DPR = 3 — и оба холста изменятся, но HiDPI сохранит резкость, а наивный станет совсем мыльным.
- **Строка статуса** — показывает текущий CSS-размер, DPR (с пометкой «override», если он не совпадает с реальным) и буферы обоих холстов.
- **Периодический опрос DPR раз в 500 мс** — если пользователь зумит страницу, демо перерисовывается автоматически, без кнопки «обновить». Правило проекта: если после действия пользователь ожидает результат, UI обновляется сам.

## 21.1.10. Wow-момент

На обычном экране разница не видна — обе панели выглядят одинаково. Это нормально, но не показательно.

Что делать:

1. **Ctrl+= дважды.** Зум страницы 200%. `devicePixelRatio` мгновенно станет 2. Через полсекунды (опрос) демо перерисуется, и разница появится прямо на экране: левая панель станет мыльной, правая останется резкой.
2. **Поставьте override DPR = 3, галочку «авто» снимите.** На обычном экране поведение то же: наивный холст замыливается всё сильнее, HiDPI держит резкость.

Это не «показываем числа», а показываем **на живом экране**: то, что человек только что читал в тексте, видно глазами.

## 21.1.11. Чему это учит

Первое правило: **размер буфера ≠ размер элемента**. Пока это не осознано, любые HiDPI-объяснения пролетают мимо. Разница видна в DevTools — в свойствах `<canvas>` рядом стоят `width: 800` и `style: "width: 400px"`, и нужно понять, что это разные вещи.

Второе: **DPR — динамический**. Записывать его в константу при загрузке страницы — ошибка. Пользователь может изменить зум, перетащить окно на другой монитор, поменять системные настройки. Единственный надёжный способ — читать `window.devicePixelRatio` там, где это важно, и подписываться на изменения через периодический опрос или `matchMedia`.

Третье: **`ctx.scale(dpr, dpr)` — обязательная часть, а не оптимизация**. Без неё холст будет правильного разрешения, но всё нарисованное сожмётся в левый верхний угол: рисование в координатах 0..800 попадает в буфер 800×400, а на экране показывается только область 0..400. Масштаб нужен ровно для того, чтобы координаты CSS и координаты рисования снова совпали.

Четвёртое: **климп DPR — защита, а не оптимизация**. `NaN` ломает canvas API (не паникует, но рисует непонятно что). Бесконечность умножает буфер до размеров, на которые нет памяти. Клампить в `[1, 4]` — стандартная практика.

Пятое: **тесты ловят семантику, компилятор — нет**. `clamp_dpr` компилируется на любой корректной сигнатуре. Но если `+∞` уходит в `1.0` вместо `4.0` — это ошибка логики, и её видит только тест. В нашей подглаве один из 8 тестов ловил именно это.

## 21.1.13. Итог

`<canvas>` — это **буфер пикселей** плюс **элемент на странице**. Два независимых размера, между которыми браузер делает масштабирование. На обычном экране разница не видна, на Retina — критична. Правильная формула — три строки: буфер × DPR, CSS-размер в пикселях, `ctx.scale(dpr, dpr)`. Защита от аномалий — кламп `[1, 4]` с явной обработкой `NaN`. Понимание этого — фундамент всего остального в главе 21.

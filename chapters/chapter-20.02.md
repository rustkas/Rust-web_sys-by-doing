# Глава 20.2. Object URL: жизненный цикл и утечки

## 20.2.1. Что такое Object URL

`URL.createObjectURL(blob)` возвращает строку вида `blob:https://origin/uuid`. Это не сам файл и не data-URL с копией байт — это **дескриптор записи в реестре URL**. Браузер заводит внутреннюю запись `{ uuid → Blob }` и держит её, пока вы не вызовете `URL.revokeObjectURL(url)`.

Пока запись в реестре жива, байты Blob **не могут быть собраны GC**. Даже если в Rust-коде у вас уже нет ни одной ссылки на `Blob`, браузер продолжит держать его в куче. Это ключевой факт подглавы: `web_sys::Blob` — не владелец байтов. Владеет ими реестр URL.

```rust
let blob = Blob::new_with_u8_array_sequence(&parts)?;
let url = Url::create_object_url_with_blob(&blob)?;   // +1 запись в реестре
// ... используем url в <img>, <a>, fetch() ...
Url::revoke_object_url(&url)?;                         // −1 запись; Blob свободен
```

Между этими двумя вызовами лежит вся семантика Object URL: **create/revoke — парная операция**. Пропущенный revoke = утечка. `Drop` для `Blob` в Rust тут не помогает: `Drop` уничтожает обёртку JS-объекта, но реестр URL держит Blob независимо.

### Три вещи, которые ломают интуицию

1. **Утечка невидима в DevTools.** Снапшот heap показывает `Blob` внутри `URLStore`, а не там, где вы его создавали. Источник в вашем коде придётся искать через Allocation instrumentation.
2. **GC ленив.** Даже после корректного `revoke` `usedJSHeapSize` падает не мгновенно — сборщик запускается по своим правилам. «Память не вернулась сразу» — норма, а не баг.
3. **`revoke` не отменяет уже открытые ссылки.** Если `<img src="blob:...">` уже загружен, revoke не помешает картинке отображаться. Но повторный `fetch(url)` после revoke упадёт. Revoke — это про реестр, не про потребителей.

### Где утечка прячется в реальном коде

- `URL.createObjectURL(file)` в `<img src=...>`, где `src` забыли снять перед revoke.
- `Closure`, который держит строку URL и живёт дольше, чем нужно.
- Глобальный `Map<String, String>` — реестр URL в JS-мосте, который не чистится.
- Цикл по файлам: URL создаётся на каждой итерации, revoke забыт в одной из веток `if`.

## 20.2.2. Что мы строим

Мини-лабораторию, которая делает утечку **видимой и измеримой**. Демо состоит из четырёх слоёв:

| Слой | Что показывает |
|---|---|
| Кнопки | create / revoke / forget / GC — управление реестром |
| График | динамику двух метрик во времени |
| Таблицы | конкретику: каждый URL, каждый замер heap, сводку состояния |
| Вводный текст и tooltips | семантику операций «на человеческом» |

Ключевая идея: **одна метрика врёт, две — нет**. Число живых URL обнуляется после «Забыть», heap остаётся высоким. Разрыв между ними и есть утечка.

## 20.2.3. Различие трёх операций

Это ядро главы. Три действия выглядят похоже, но делают принципиально разное.

| Операция | Строк URL в Rust | Записей в URL-реестре | Что с байтами Blob |
|---|---|---|---|
| `URL.createObjectURL(blob)` | +1 | +1 | Держатся реестром, GC их не трогает |
| `URL.revokeObjectURL(url)` | 0 (вы контролируете) | −1 | Становятся доступны GC — но не сразу |
| «Забыть» (потерять строку) | −1 | **0** | Остаются в реестре до выгрузки документа — утечка |

Третья строка — самое важное в подглаве. Потерять строку в Rust ≠ освободить Blob. Реестр URL **не знает**, что вы «забыли» переменную. Он знает только про `revokeObjectURL`. Именно поэтому все примеры кода в интернете, где blob-URL передаётся куда-то в замыкание и теряется, — это утечки, которых не видно в heap snapshot.

Это же объясняет правило проекта:

> Любая «отменить/удалить» операция должна быть идемпотентной. `revokeObjectURL` для уже отозванного URL — no-op, ошибки нет. «Освободить всё» можно нажимать сколько угодно раз, результат тот же.

## 20.2.4. Как измерять утечку

`performance.memory.usedJSHeapSize` — нестандартный API, доступен в Chromium. В Firefox его нет; демо должно деградировать мягко: показывать «н/д (нужен Chromium)» вместо нулевой линии.

```rust
pub fn read_used_heap_bytes() -> Option<f64> {
    let global = js_sys::global();
    let perf = Reflect::get(&global, &JsValue::from_str("performance")).ok()?;
    let mem = Reflect::get(&perf, &JsValue::from_str("memory")).ok()?;
    Reflect::get(&mem, &JsValue::from_str("usedJSHeapSize"))
        .ok()?
        .as_f64()
}
```

`Option<f64>` честно сигналит «недоступно». `web-sys` не экспортирует `performance.memory` (нестандарт), поэтому обращаемся через `Reflect::get` — универсальный способ дотянуться до любого JS API, независимо от текущей версии `web-sys`.

Форсировать GC можно через `window.gc()`, но только если Chrome запущен с флагом `--js-flags="--expose-gc"`. Без флага — тихий no-op:

```rust
pub fn try_request_gc() -> bool {
    let global = js_sys::global();
    let Ok(candidate) = Reflect::get(&global, &JsValue::from_str("gc")) else {
        return false;
    };
    let Ok(func) = candidate.dyn_into::<js_sys::Function>() else {
        return false;
    };
    func.call0(&JsValue::UNDEFINED).is_ok()
}
```

Это второе проявление правила проекта: **если API может быть недоступно — API возвращает Option, а не паникует**. Демо обязано работать и в Firefox, и в Chrome, и в Safari.

## 20.2.5. Модуль `object_url_lifecycle`

Всё, что относится к подглаве, собрано в одном файле `src/object_url_lifecycle.rs`:

```rust
pub fn make_payload_blob(size_kb: usize) -> Result<Blob, JsValue>
pub fn create_object_url(blob: &Blob) -> Result<String, JsValue>
pub fn revoke_object_url(url: &str)
pub fn read_used_heap_bytes() -> Option<f64>
pub fn read_heap_limit_bytes() -> Option<f64>
pub fn try_request_gc() -> bool
```

И структура-бухгалтер:

```rust
pub struct ObjectUrlLab {
    live: Vec<String>,
    created: usize,
    revoked: usize,
    forgotten: usize,
}
```

Пять счётчиков — минимальный инвариант для продакшена. Если вы создаёте blob-URL где-то в коде, у вас должно быть место, где видно: сколько создано, сколько отозвано, сколько потеряно. Это то же самое, что `Arc::strong_count` — дешёвая проверка здоровья.

Тесты фиксируют семантику:

- `lab_counts_are_consistent` — три счётчика после leak/release/release_all сходятся;
- `release_all_is_idempotent` — повторный клик не ошибка;
- `forget_drops_rust_handles_without_revoking` — «забыть» уменьшает `live`, но не увеличивает `revoked`;
- `heap_readers_and_gc_are_optional` — в Firefox функции возвращают None/false, не паника.

## 20.2.6. Демо: что видит студент

Демо-пример собирает всё это в один экран. Сверху вниз:

**1. Вводный текст.** Три абзаца: что за лаборатория, как читать таблицу, типичный сценарий утечки. Студент открывает файл и сразу понимает, что происходит.

**2. Строка статуса.** `живых URL: N | забыто (утечка): M | heap: X МБ`. Обновляется каждые 0.5 с.

**3. Ряд кнопок** — каждая с tooltip:

- **«Утечь 1×1MB»** — создать один blob-URL без revoke.
- **«Утечь 20×1MB»** — создать пачку.
- **«Освободить 1»** — revoke самого свежего живого URL.
- **«Освободить всё»** — revoke всех живых. Идемпотентно.
- **«Забыть (утечка)»** — пометить живые URL как забытые, **не вызывая revoke**. Это и есть утечка.
- **«Запросить GC»** — попытка вызвать `window.gc()`.

Tooltip'ы через `HtmlElement::set_title(...)` — нативные, работают без CSS и без `Closure`.

**4. График и таблица heap рядом.** Синяя линия — `usedJSHeapSize` во времени, зелёная — число живых URL. Автомасштаб каждой серии независимый, иначе миллионы байт подавят десятки URL. Справа — таблица последних 8 замеров с конкретными цифрами: `t, с` и `heap, МБ`.

**5. Таблица «Детально: blob-URL текущей сессии».** Каждая строка — один URL:

| # | статус | размер | создан | закрыт | проверить | URL |
|---|---|---|---|---|---|---|
| 42 | жив | 1 МБ | 3.21s | — | открыть | `blob:https://…` |
| 41 | забыт (утечка) | 1 МБ | 3.19s | 5.02s | — | `blob:https://…` |
| 40 | освобождён | 1 МБ | 3.18s | 4.87s | — | `blob:https://…` |

Живые URL кликабельны — открывают Blob в новой вкладке. Студент убеждается, что `blob:...` — это не «заглушка», а реально существующая ссылка в памяти браузера. Наведение на ячейку URL показывает полный текст в tooltip'е — при обрезке длинных URL до `…`.

Строки с забытыми URL подсвечены красным. Строки с освобождёнными — серые (уже не живут). Строки с живыми — обычные, с зелёным статусом.

**6. Таблица «Что где живёт прямо сейчас».** Сводка:

```
Всего создано blob-URL (сессия)         42
  живых (revoke возможен)                12
  освобождено (revoke вызван)            20
  забыто (revoke невозможен)             10
Записей в URL-реестре (жив + забыт)      22
Оценка удержанных Blob-байт           22.00 МБ
usedJSHeapSize (факт)        43.21 МБ (18.3% от лимита)
```

Последняя строка — ключевая. **Забытые URL входят в «записей в реестре»**: они всё ещё держат байты. Студент видит: `забыто = 10`, `Записей = 22`, `удержано = 22 МБ`. Это и есть утечка, выраженная числом.

**7. Таблица «Семантика операций».** Три строки — резюме главы. Эту таблицу стоит распечатать и повесить на стену.

**8. Footnote.** Напоминание: в реальном коде строка URL была бы потеряна, но и тогда Blob держался бы реестром. Revoke — единственный способ освободить Blob.

## 20.2.7. Wow-сценарий

Три клика, которые показывают суть подглавы лучше тысячи слов:

1. **«Утечь 20×1MB»** — синяя линия растёт на ~20 МБ, зелёная — на 20.
2. **«Забыть (утечка)»** — зелёная линия падает в 0 (Rust-строки потеряны), синяя **остаётся на месте**. В таблице сводки: `живых = 0`, `забыто = 20`, `Записей в реестре = 20`, `удержано = 20 МБ`.
3. **«Запросить GC»** — синяя линия **не падает**, потому что URL-реестр держит байты. Единственный способ освободить их — выгрузить документ.

Тот же сценарий с «Освободить всё» вместо «Забыть» даёт другой результат: `Записей в реестре = 0`, синяя линия через несколько тиков проседает. **Это контраст, который запоминается.**

## 20.2.8. Правила проекта, зафиксированные в подглаве

1. **`revoke` — парный к `create`.** Если в коде есть `createObjectURL`, рядом должен быть `revokeObjectURL`. Точка. Никаких «это освободит GC».
2. **`Option<T>` для нестандартных API.** `performance.memory` — не гарантирован; `window.gc` — не гарантирован. API возвращает `Option`, UI честно говорит «н/д (нужен Chromium)».
3. **Две метрики лучше одной.** Живые URL + heap вместе дают картину, которая недоступна ни одной из них по отдельности. Число живых URL без heap не покажет утечку; heap без числа URL не скажет, откуда она.
4. **Таблица — не роскошь.** Интерактивное демо, где есть только график, оставляет студента с догадками. Таблица «URL → статус → время» превращает абстракцию в конкретику.
5. **Tooltips — вместо отдельной справки.** Кнопка с `title="…"` объясняет себя без переключения на другую вкладку.
6. **`format_str(format_args!(…))` вместо `format!` в tail-позиции.** Баг rust-analyzer `expected String, found ()` обходится утилитой `crate::format_str`. Правило: любой `format!` — последнее выражение `if/else`, `match`-арма, тела функции или элемента массива — оборачивается в `format_str`.
7. **`HtmlElement` → `Node` через `unchecked_into`.** Авто-deref не проходит через `Result<T, _>`; явный upcast в одной точке чище, чем аннотации на call site.

## 20.2.9. Итог

Object URL — это дескриптор записи в реестре браузера, а не сам Blob. Пока запись жива, байты держатся. `Drop` в Rust не помогает. Единственный способ освободить — `URL.revokeObjectURL`.

Утечка — это не «Blob в Rust не освободился», а «запись в реестре осталась без владельца в коде». Никакой GC её не соберёт: реестр URL для сборщика — корень. Именно поэтому `revoke` — обязательная операция, а не оптимизация.

Демо-лаборатория делает это видимым: три кнопки (создать / освободить / забыть), две метрики (живые URL и heap), четыре таблицы (URL сессии, замеры heap, сводка состояния, семантика операций) и один график. Wow-сценарий в три клика показывает разницу между «освободить» и «забыть» — то, что невозможно передать словами без визуальной опоры.

Код главы автономен: модуль `object_url_lifecycle` не зависит от других подглав, `app.rs` содержит только демо этой темы. Правила проекта (`Option` для нестандартных API, `format_str` для tail-format!, `unchecked_into` для upcast'ов) применены последовательно, чтобы код собирался без warning'ов и rust-analyzer не подчёркивал ни одну строку.

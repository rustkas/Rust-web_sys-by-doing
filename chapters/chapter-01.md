# Глава 1. Rust получает доступ к Web Platform

## 1. Rust и браузер

Исторически браузер был территорией JavaScript. Любая логика, выполняемая на стороне клиента, писалась на JS — с его динамической типизацией, сборкой мусора и неизбежными компромиссами по производительности. Rust в эту картину не вписывался: это системный язык с явным управлением памятью, строгой типизацией и zero-cost абстракциями. Он компилируется в машинный код, а не в байт-код виртуальной машины, и не предполагает наличия сборщика мусора.

Тем не менее Rust оказался в браузере. Не потому, что кто-то решил «переписать фронтенд на Rust», а потому, что появилась технология, которая позволила использовать Rust там, где JavaScript объективно слаб: в вычислительно тяжёлых задачах — обработке изображений и видео, криптографии, парсинге бинарных форматов, работе с большими объёмами данных, алгоритмах реального времени.

Эта технология — WebAssembly.

## 2. WebAssembly как среда выполнения

WebAssembly (Wasm) — это бинарный формат инструкций, который выполняется в браузере. Это не язык программирования в привычном смысле, а **цель компиляции**: вы пишете на Rust, C/C++, C# или другом языке, компилятор выдаёт `.wasm`-модуль, браузер его загружает и исполняет.

Ключевые свойства Wasm, которые делают его пригодным для наших целей:

- **Компактный бинарный формат.** Модуль `.wasm` загружается и парсится быстрее, чем эквивалентный JavaScript.
- **Предсказуемая производительность.** Wasm — низкоуровневый стековый байт-код, близкий к машинному. Он не проходит через JIT-компиляцию с её «прогревом» и деоптимизациями.
- **Безопасность.** Wasm выполняется в песочнице с изолированной линейной памятью. Модуль не имеет доступа к памяти хоста напрямую.
- **Языковая независимость.** Wasm не привязан к Rust. Это просто формат, в который можно скомпилировать любой язык с подходящим бэкендом.

Но у Wasm есть принципиальное ограничение, которое определяет всю дальнейшую архитектуру. **Wasm-модуль не умеет напрямую обращаться к браузерным API.** Он не знает, что такое `window`, `document` или `fetch`. Wasm «видит» только свою линейную память и набор импортируемых/экспортируемых функций с примитивными типами — целыми числами и числами с плавающей точкой.

Строки, объекты, массивы, замыкания — всё это за пределами базового Wasm. Чтобы Rust мог работать с браузером, нужен посредник.

## 3. JavaScript как мост к браузеру

Этим посредником становится JavaScript. Не потому, что это единственный вариант, а потому, что JS — единственный язык, который **уже** имеет полный доступ к Web Platform. Браузер предоставляет свои API именно через JavaScript: `document.querySelector()`, `fetch()`, `new Worker()` — всё это JS-вызовы.

Архитектура получается такой:

```
Rust-код (логика)
    ↓ компиляция
WebAssembly-модуль (изолированный, не знает о браузере)
    ↓ вызовы через сгенерированный «клей»
JavaScript (мост)
    ↓ нативные вызовы
Web API браузера (DOM, Fetch, Canvas, Storage...)
```

Wasm-модуль загружается в браузер, JavaScript-код инстанцирует его и получает доступ к экспортированным функциям. Когда Rust-функция хочет, например, записать что-то в DOM, она не может сделать это напрямую — она вызывает **импортированную** JavaScript-функцию, которая уже выполняет `document.createElement()` и возвращает результат обратно в Wasm.

Этот мост — не просто техническая деталь. Это **граница**, на которой происходят преобразования типов, копирование данных и потенциальные потери производительности. Понимание этой границы — половина успеха в работе с `web_sys`.

## 4. `wasm-bindgen`

Писать JS-клей вручную — больно. Для каждой функции нужно вручную описывать, какие аргументы она принимает, как преобразовать строку Rust в строку JS, как вернуть объект обратно. `wasm-bindgen` автоматизирует эту работу.

`wasm-bindgen` — это Rust-библиотека и CLI-инструмент, который обеспечивает высокоуровневое взаимодействие между Wasm-модулями и JavaScript. Он делает две вещи:

**Импорт JS-функций в Rust.** Вы объявляете внешнюю функцию с атрибутом `#[wasm_bindgen]`, и `wasm-bindgen` генерирует код, который при вызове из Rust корректно преобразует аргументы и вызывает соответствующую JS-функцию.

**Экспорт Rust-функций в JS.** Вы помечаете функцию атрибутом `#[wasm_bindgen]`, и она становится доступной из JavaScript — с автоматической конвертацией типов.

```rust
use wasm_bindgen::prelude::*;

#[wasm_bindgen]
pub fn greet(name: &str) -> String {
    format!("Привет, {}!", name)
}

#[wasm_bindgen]
extern "C" {
    #[wasm_bindgen(js_namespace = console)]
    fn log(s: &str);
}
```

`wasm-bindgen` поддерживает не только примитивы, но и **богатые типы**: `String`, `Vec`, `Result`, срезы, структуры, замыкания. Он генерирует TypeScript-определения для экспортируемого Rust-кода. Именно этот инструмент превращает Wasm из «изолированного вычислительного ядра» в полноценного участника браузерного приложения.

## 5. `web_sys`

`wasm-bindgen` решает проблему **связи** между Rust и JS, но не решает проблему **API**. Чтобы вызвать `document.createElement()`, вам всё ещё нужно вручную объявить эту функцию через `extern "C"`, знать её сигнатуру, разобраться с типами возвращаемых значений. Для сотен браузерных API это непрактично.

`web-sys` — это crate, который предоставляет **готовые привязки ко всем Web API** браузера. Он генерируется полностью механически из **WebIDL** — языка описания интерфейсов, на котором специфицированы браузерные API.

Структура crate'а:

- `webidls/enabled/*.webidl` — исходные описания интерфейсов
- `build.rs` — запускает WebIDL-фронтенд `wasm-bindgen` и генерирует привязки
- `src/lib.rs` — просто включает сгенерированный код

Поскольку API браузера огромен, `web-sys` использует **Cargo features**: каждый тип соответствует отдельной feature, и по умолчанию crate почти пуст. Чтобы использовать `Window`, нужно включить feature `Window`; чтобы использовать `HtmlCanvasElement` — feature `HtmlCanvasElement`. Это сделано для того, чтобы время компиляции оставалось разумным, а бинарник не раздувался неиспользуемыми привязками.

Именно поэтому `web-sys` — не «ещё один фреймворк», а **типизированная проекция Web Platform в Rust**. Он не придумывает абстракции, а даёт прямой, проверенный и корректный доступ к браузерным API.

## 6. `js_sys`

Между `wasm-bindgen` и `web_sys` есть промежуточный слой — `js_sys`. Этот crate предоставляет привязки к **глобальным JavaScript-объектам**, которые гарантированно существуют в любом JS-окружении по стандарту ECMAScript.

Речь о таких типах, как `Array`, `Object`, `Function`, `Map`, `Set`, `Promise`, `Date`, `ArrayBuffer`, `Uint8Array`. Это не браузерные API — это базовые строительные блоки JavaScript как языка.

Разделение простое:

| Crate | Что покрывает |
|---|---|
| `js_sys` | ECMAScript: `Array`, `Object`, `Promise`, `Map`, `Date`, типизированные массивы |
| `web_sys` | Web Platform: `Window`, `Document`, `HtmlElement`, `fetch`, `Canvas`, `Storage` |

`web_sys` зависит от `js_sys` (и реэкспортирует его), но не наоборот. Это отражено в структуре crate'ов.

## 7. Архитектура Rust → WASM → JavaScript → Web API

Соберём всё вместе. Когда Rust-код вызывает браузерный API, происходит следующая последовательность:

**Шаг 1. Rust-код.** Вы пишете `web_sys::window().unwrap().document().unwrap()`. Это обычный Rust-код, но он компилируется в Wasm.

**Шаг 2. Компиляция.** `rustc` с target `wasm32-unknown-unknown` генерирует `.wasm`-модуль. Вызовы `web_sys`-функций становятся **импортами** Wasm — модуль ожидает, что хост предоставит эти функции при инстанцировании.

**Шаг 3. Генерация клея.** `wasm-bindgen` анализирует `.wasm`-модуль и генерирует JavaScript-файл, который:
- инстанцирует Wasm-модуль;
- предоставляет импортируемые функции (те самые `web_sys`-обёртки);
- экспортирует Rust-функции для вызова из JS.

**Шаг 4. JavaScript-клей.** Сгенерированный JS-код содержит функции вроде `__wbg_window_...`, которые вызывают `window` в глобальном контексте браузера и возвращают результат обратно в Wasm — уже в виде `JsValue` или конкретного типа.

**Шаг 5. Web API.** Браузер выполняет `window`, `document.createElement()` и т.д. Результат возвращается по той же цепочке в обратном порядке.

Ключевое следствие: **каждый переход через границу Rust↔JS стоит времени**. Это не «медленно» само по себе, но при неправильном проектировании — когда через границу гоняются тысячи мелких вызовов — производительность может просесть. Поэтому в главе 54 («Designing the JS ↔ WASM Boundary») мы будем подробно разбирать, как минимизировать эти переходы.

## 8. Где заканчивается Rust и начинается Web Platform

Это, пожалуй, самый важный вопрос главы — и всей книги.

Rust в браузере — не замена JavaScript. Это **дополнение** к нему. Граница между ними определяется не идеологией, а задачей.

**Rust берёт на себя:**
- Вычислительно тяжёлую логику (алгоритмы, обработка данных, парсинг)
- Работу с бинарными форматами (изображения, видео, документы)
- Криптографию
- Протоколы (сетевые, аппаратные)
- Состояние приложения, требующее строгой типизации и предсказуемости

**JavaScript и Web Platform берут на себя:**
- DOM: создание, изменение, удаление элементов
- События: подписка, обработка, распространение
- Навигацию, историю, URL
- Все асинхронные API браузера: `fetch`, `Promise`, `Worker`
- Рендеринг: Canvas, WebGL, CSS

`web_sys` — это **мост** между этими двумя мирами. Он не пытается «заменить браузер» Rust-кодом. Он даёт Rust-коду **доступ** к браузеру — ровно настолько, насколько это нужно для решения конкретной задачи.

В следующей главе мы разберём, как устроен `web_sys` изнутри: от WebIDL до Cargo features, и почему его API выглядит именно так, а не иначе.

---

**Итог главы:**

- WebAssembly — это цель компиляции, а не язык. Rust компилируется в `.wasm`.
- Wasm-модуль изолирован и не имеет прямого доступа к браузерным API.
- JavaScript служит мостом: Rust вызывает импортированные JS-функции, JS выполняет нативные вызовы.
- `wasm-bindgen` автоматизирует генерацию моста и конвертацию типов.
- `web_sys` — механически сгенерированные привязки ко всем Web API из WebIDL.
- `js_sys` — привязки к ECMAScript-объектам (`Array`, `Promise`, `Map`).
- Каждый переход через границу Rust↔JS — это стоимость. Проектируйте границу осознанно.
- Rust не заменяет Web Platform. Он её дополняет в тех задачах, где нужна производительность и строгая типизация.
